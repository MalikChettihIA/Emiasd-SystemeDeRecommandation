## 1. 📊 Types d'Évaluation {#types-evaluation}

Il existe trois grandes approches pour évaluer un système de recommandation :

### 1.1 🔬 Offline Evaluation (Évaluation Hors-ligne)

**Définition :**
> Évaluation réalisée sur des **datasets préalablement collectés** et qui simulent le comportement utilisateur.

**Processus :**
```
Utilisateurs réels → Plateforme → Dataset collecté
                                        ↓
                                   (historique)
                                        ↓
                       Training data → [RS Model] → Evaluation
                       Test data ────────────┘
```

**✅ Avantages (Pros) :**
- **Pas d'interaction avec utilisateurs réels** : Pas de risque
- **Reproductibilité** : Expériences répétables avec mêmes données
- **Rapidité** : Tests multiples en parallèle
- **Coût faible** : Pas de déploiement nécessaire
- **Comparaison facile** : Benchmarking entre algorithmes

**❌ Inconvénients (Cons) :**
- **Ne mesure PAS l'influence réelle** du RS sur le comportement utilisateur
- **Biais de sélection** : Dataset reflète l'ancien système
- **Pas de feedback loop** : Ne capture pas les effets dynamiques
- **Métriques limitées** : Certaines propriétés difficiles à mesurer offline

**Quand utiliser :**
- Phase de développement et prototypage
- Comparaison d'algorithmes
- Optimisation des hyperparamètres
- Avant tout déploiement en production

---

### 1.2 👥 User Study (Étude Utilisateur)

**Définition :**
> Recrutement d'un **petit nombre d'utilisateurs** et observation de leur interaction avec le RS dans un environnement contrôlé.

**Processus :**
```
Recrutement → Protocole expérimental → Observation/Questionnaires → Analyse qualitative
```

**✅ Avantages (Pros) :**
- **Insights qualitatifs** : Comprendre le "pourquoi"
- **Aspects UX** : Évaluer interface, satisfaction, confiance
- **Explainability** : Tester si explications sont comprises
- **Serendipity subjective** : Mesurer surprises agréables

**❌ Inconvénients (Cons) :**
- **Biais d'échantillonnage** : Participants non représentatifs
- **Effet Hawthorne** : Comportement modifié car observé
- **Petite taille** : Résultats non généralisables statistiquement
- **Coûteux** : Temps et ressources nécessaires
- **Difficile à reproduire**

**Quand utiliser :**
- Tests d'interface et UX
- Validation de concepts
- Compréhension approfondie du ressenti utilisateur
- Complément aux métriques quantitatives

---

### 1.3 🌐 Online Evaluation (Évaluation En-ligne)

**Définition :**
> **A/B testing** sur un système de recommandation **déployé en production** avec de vrais utilisateurs.

**Processus :**
```
Traffic réel → Séparation aléatoire
                     ↓                    ↓
               Groupe A (contrôle)   Groupe B (variant)
                RS actuel              Nouveau RS
                     ↓                    ↓
               Métriques A          Métriques B
                     └──────────┬──────────┘
                           Comparaison statistique
```

**✅ Avantages (Pros) :**
- **Evidence la plus forte** : Mesure impact réel
- **Métriques business** : CTR, conversions, revenue, engagement
- **Effet causal** : Attribuer changements au système
- **Conditions réelles** : Pas de biais expérimental

**❌ Inconvénients (Cons) :**
- **Risque utilisateur** : Peut dégrader expérience du Groupe B
- **Coût élevé** : Infrastructure et traffic nécessaires
- **Temps long** : Attendre significativité statistique
- **Complexité** : Confounding factors, effets de réseau
- **Éthique** : Implications de tester sur utilisateurs réels

**Quand utiliser :**
- Validation finale avant rollout complet
- Mesure d'impact business réel
- Fine-tuning en production
- Décisions stratégiques majeures

## 2. 🔬 Offline Evaluation Détaillée {#offline-evaluation}

### 2.1 Architecture générale

```
┌─────────────────────────────────────────────────┐
│         Dataset Historique Complet              │
│  (Interactions utilisateurs-items collectées)   │
└────────────────┬────────────────────────────────┘
                 │
          ┌──────┴──────┐
          ↓             ↓
   Training Set    Test Set
        │              │
        ↓              │
   [Train Model]       │
        │              │
        ↓              ↓
   [Predictions] → [Evaluation]
                       ↓
                   Métriques
```

### 2.2 Pourquoi séparer Train/Test ?

**Problème de l'overfitting :**
- Modèle "apprend par cœur" les données d'entraînement
- Mauvaise généralisation sur nouvelles données

**Solution :**
- **Training set** : Entraîner le modèle
- **Test set** : Évaluer performance sur données "non vues"
- Simule comment le modèle se comportera en production

## 3. 📂 Méthodes de Split des Données {#split-methods}

### 3.1 Random Split (Division Aléatoire)

**Principe :**
Séparer aléatoirement les interactions en train/test.

```
Dataset complet
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Après random split (80/20) :
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Training (80%)              Test (20%)
```

**Caractéristiques :**
- Simple à implémenter
- Ratio typique : 80/20 ou 70/30
- Chaque interaction a même probabilité d'être dans test

**⚠️ Problèmes :**
- **Ne respecte pas l'ordre temporel**
- Peut "fuiter" information du futur dans le passé
- Pas réaliste pour systèmes temporels

**Quand utiliser :**
- Données sans composante temporelle forte
- Quick prototyping
- Datasets statiques

---

### 3.2 K-Fold Cross Validation

**Principe :**
Diviser dataset en K parts égales (folds) et itérer.

```
Dataset
┌─────────────────────────────────────┐

Fold 1: [Test]──────[Training────────]
Fold 2: [Training]──[Test]───[Training]
Fold 3: [Training───]──[Test]─[Training]
...
Fold k: [Training──────────────][Test]
```

**Algorithme :**
1. Diviser données en K folds
2. Pour chaque fold i :
   - Fold i = Test set
   - Folds restants = Training set
   - Entraîner modèle et évaluer
3. Moyenne des K résultats = Performance finale

**✅ Avantages :**
- Utilise toutes les données pour train ET test
- Réduit variance de l'estimation
- Meilleure utilisation de données limitées

**❌ Inconvénients :**
- K fois plus coûteux (K entraînements)
- Ne respecte pas temporalité

**Paramètres typiques :**
- K = 5 ou K = 10 courant
- K = n (Leave-One-Out) : chaque point testé séparément

---

### 3.3 Given-N Split (Split à N interactions)

**Principe :**
Pour chaque utilisateur, utiliser les **N premières interactions** pour training, le reste pour test.

**Exemple avec N = 3 :**

```
        😊 User 1  😊 User 2  😊 User 3  😊 User 4  😊 User 5
        ─────────────────────────────────────────────────────
Inter#1 🟩 Train   🟩 Train   🟩 Train   🟩 Train   🟩 Train
Inter#2 🟩 Train   🟩 Train   🟩 Train   🟩 Train   🟩 Train  
Inter#3 🟩 Train   🟩 Train   🟩 Train   🟩 Train   🟩 Train
        ─────────────────────────────────────────────────────
Inter#4 🟥 Test               🟥 Test    🟥 Test
Inter#5 🟥 Test                          
```

**Caractéristiques :**
- Chaque utilisateur contribue au train (N interactions)
- Test = interactions restantes par utilisateur
- Simule cold-start modéré (utilisateurs avec peu d'historique)

**✅ Avantages :**
- Réaliste : modélise utilisateurs actifs vs nouveaux
- Contrôle du niveau de cold-start

**❌ Inconvénients :**
- Utilisateurs avec < N interactions exclus
- Déséquilibré si users ont historiques variés

---

### 3.4 Chronological Split (Split Temporel)

**Principe :**
Séparer selon le **temps** : interactions avant date T = training, après = test.

```
Timeline ──────────────────────────────────────────────→
         │                                    │
         │         Training Set               │  Test Set
         │  (avant date T)                    │  (après T)
         │                                    │
   🎬🟩  🎬🟩  🎬🟩  🎬🟩 | 🎬🟥  🎬🟥
   😊    😊    😊    😊   │  😊    😊
```

**Caractéristiques :**
- **Respecte l'ordre temporel**
- Simule prédiction du futur basée sur le passé
- Le plus réaliste pour production

**✅ Avantages :**
- **Réalisme maximal** : Reproduit déploiement réel
- Capture effets temporels (saisonnalité, tendances)
- Évite data leakage

**❌ Inconvénients :**
- Test set peut être très différent de training
- Concept drift possible
- Peu de données test si période courte

**Quand utiliser :**
- **Recommandé pour tout système avec composante temporelle**
- E-commerce, streaming, news, etc.
- Évaluation la plus proche de la production

## 4. 🎯 Critères d'Évaluation {#evaluation-criteria}

Un bon système de recommandation doit être évalué sur **plusieurs dimensions** :

### 4.1 Accuracy (Précision)
> À quel point les prédictions sont-elles précises ?

- Prédire correctement les ratings
- Prédire correctement les préférences

### 4.2 Coverage (Couverture)
> Quelle proportion du catalogue est couverte par les recommandations ?

- **User coverage** : % utilisateurs recevant des recommandations
- **Item coverage** : % items jamais recommandés
- Éviter que seuls items populaires soient recommandés

### 4.3 Diversity (Diversité)
> Les recommandations sont-elles variées ?

- Diversité **intra-list** : Variété au sein d'une liste de recommandations
- Diversité **inter-list** : Variété entre listes pour même utilisateur au fil du temps
- Éviter filter bubbles

### 4.4 Serendipity (Sérendipité)
> Les recommandations pertinentes sont-elles surprenantes ?

- Items que l'utilisateur **aime** mais ne **connaissait pas**
- Balance entre familier et nouveau
- Difficile à mesurer objectivement

### 4.5 Explainability (Explicabilité)
> Peut-on expliquer et justifier les recommandations ?

- Transparence de l'algorithme
- Confiance utilisateur
- "Vous pourriez aimer ceci car..."

## 5. 📐 Métriques d'Accuracy {#accuracy-metrics}

### 5.1 Mean Absolute Error (MAE)

**Objectif :**
Mesurer l'erreur moyenne entre ratings prédits et réels.

**Formule :**
```
MAE = (1/|T|) × Σ |r_ui - r̂_ui|
              (u,i)∈T
```

Où :
- **T** : Ensemble des paires (user, item) dans test set
- **r_ui** : Rating réel de user u pour item i
- **r̂_ui** : Rating prédit

**Exemple :**

| User | Actual ⭐ | Predicted ⭐ | Error |
|------|-----------|--------------|-------|
| 😊 | ⭐⭐⭐⭐⭐ (5) | ⭐⭐⭐⭐ (4) | 1 |
| 😊 | ⭐ (1) | ⭐⭐⭐⭐ (4) | 3 |
| 😊 | ⭐⭐⭐ (3) | ⭐⭐⭐⭐⭐ (5) | 2 |
| 😊 | ⭐⭐⭐⭐ (4) | ⭐⭐⭐⭐ (4) | 0 |
| 😊 | ⭐⭐ (2) | ⭐ (1) | 1 |

**Calcul :**
```
MAE = (1 + 3 + 2 + 0 + 1) / 5 = 7 / 5 = 1.4
```

**Interprétation :**
- En moyenne, les prédictions se trompent de **1.4 étoiles**
- Plus MAE est **petit**, meilleur est le modèle
- MAE = 0 → Prédictions parfaites

**Caractéristiques :**
- ✅ Facile à interpréter (même unité que ratings)
- ✅ Robuste aux outliers (erreur linéaire)
- ❌ Traite toutes erreurs également (erreur de 1 = erreur de 5)

---

### 5.2 Root Mean Squared Error (RMSE)

**Objectif :**
Mesurer l'erreur quadratique moyenne (pénalise davantage les grandes erreurs).

**Formule :**
```
RMSE = √(MSE) = √[(1/|T|) × Σ (r_ui - r̂_ui)²]
                           (u,i)∈T
```

**Exemple (même données que MAE) :**

| User | Actual | Predicted | Error | Error² |
|------|--------|-----------|-------|--------|
| 😊 | 5 | 4 | 1 | 1 |
| 😊 | 1 | 4 | 3 | 9 |
| 😊 | 3 | 5 | 2 | 4 |
| 😊 | 4 | 4 | 0 | 0 |
| 😊 | 2 | 1 | 1 | 1 |

**Calcul :**
```
MSE = (1 + 9 + 4 + 0 + 1) / 5 = 15 / 5 = 3
RMSE = √3 ≈ 1.73
```

Mais selon la slide : **RMSE = 3** (probablement erreur dans calcul slide ou données différentes)

**Interprétation :**
- **RMSE > MAE** toujours (sauf si toutes erreurs identiques)
- Pénalise fortement les grandes erreurs
- Plus sensible aux outliers

**Comparaison MAE vs RMSE :**

| Métrique | Formule | Sensibilité outliers | Interprétation |
|----------|---------|---------------------|----------------|
| **MAE** | Valeur absolue | Faible | Erreur moyenne typique |
| **RMSE** | Racine carrée | Élevée | Erreur avec pénalité sur grosses erreurs |

**Quand utiliser :**
- **MAE** : Quand toutes erreurs égales en importance
- **RMSE** : Quand grandes erreurs sont critiques (ex: prédire rating 1 alors que réel est 5)

### 5.3 Métriques pour Top-N Recommendations

Pour les systèmes de recommandation, on s'intéresse souvent au **classement** plutôt qu'aux valeurs exactes.

#### Notations

```
┌────────────────────────────────────┐
│     Items Irrelevant (TN + FP)     │  ← Top-N recommendations
│  ┌──────────────┐                  │
│  │   TN    │ FP │                  │
│  └──────────────┘                  │
├────────────────────────────────────┤
│     Items Relevant (FN + TP)       │
│  ┌──────────────┐                  │
│  │   FN    │ TP │                  │
│  └──────────────┘                  │
└────────────────────────────────────┘
```

- **TP (True Positive)** : Items pertinents recommandés ✅
- **FP (False Positive)** : Items non pertinents recommandés ❌
- **TN (True Negative)** : Items non pertinents non recommandés (pas important)
- **FN (False Negative)** : Items pertinents NON recommandés (missing)

---

#### 5.3.1 Recall@N (Rappel)

**Définition :**
Proportion des **items pertinents** qui sont **recommandés** dans le Top-N.

**Formule :**
```
Recall@N = TP / (FN + TP) = #relevant recommended / #relevant items
```

**Assumption :**
> **Missing Not As Random** : Les items non-pertinents sont **plus susceptibles** d'être manquants que les items pertinents.

**Interprétation :**
- "Sur tous les items que l'utilisateur aime, combien en ai-je recommandés ?"
- Recall = 1.0 → Tous items pertinents sont recommandés ✅
- Recall = 0.0 → Aucun item pertinent recommandé ❌

**Exemple :**
```
Utilisateur aime : {A, B, C, D, E}  (5 items pertinents)
Recommandations Top-5 : {A, B, X, Y, Z}
TP = 2 (A, B recommandés)
FN = 3 (C, D, E manquants)

Recall@5 = 2 / (2 + 3) = 2/5 = 0.4 = 40%
```

---

#### 5.3.2 Precision@N (Précision)

**Définition :**
Proportion des **items recommandés** qui sont **pertinents**.

**Formule :**
```
Precision@N = TP / (FP + TP) = #relevant recommended / #recommended items
```

**Assumption :**
> **All Missing As Negative** : Tous les ratings manquants sont considérés comme **non pertinents**.

**Interprétation :**
- "Sur tous les items que j'ai recommandés, combien sont réellement pertinents ?"
- Precision = 1.0 → Toutes recommandations sont pertinentes ✅
- Precision = 0.0 → Aucune recommandation pertinente ❌

**Exemple :**
```
Recommandations Top-5 : {A, B, X, Y, Z}
Pertinents : A, B
Non pertinents : X, Y, Z

TP = 2
FP = 3

Precision@5 = 2 / (2 + 3) = 2/5 = 0.4 = 40%
```

---

#### 5.3.3 Visualisation Recall vs Precision

```
┌─────────────────────────────────┐
│  🟢 Irrelevant items            │
│    ┌──────────┐                 │  ← Top-N recs
│    │ TN  │ FP │◄─── missing     │
│    └──────────┘                 │
├─────────────────────────────────┤
│  🟣 Relevant items              │
│    ┌──────────┐                 │
│    │ FN  │ TP │                 │
│    └──────────┘                 │
└─────────────────────────────────┘

Recall = TP / (FN + TP)    ← Combien de pertinents récupérés ?
Precision = TP / (FP + TP)  ← Combien de recommandés sont pertinents ?
```

## 6. 📊 Métriques de Ranking {#ranking-metrics}

Les métriques de ranking prennent en compte l'**ordre** des recommandations, pas seulement leur présence.

### 6.1 Discounted Cumulative Gain (DCG@N)

**Principe :**
Récompenser les items pertinents **placés haut** dans la liste.

**Formule :**
```
DCG_u@N = Σ (rel_ui) / log₂(i + 1)
         i=1 to N
```

Où :
- **rel_ui** = 1 si item à position i est pertinent, 0 sinon
- **i** = position dans la liste (1 à N)
- **log₂(i+1)** = facteur de discount (pénalise positions basses)

**Exemple :**

```
Recommendation list pour utilisateur 😊 :

Position  Film          Pertinent?  rel_ui  log₂(i+1)  Gain
────────────────────────────────────────────────────────────
i=1       Barbie        👍          1       1.0        1.00
i=2       Anatomy       👎          0       1.58       0.00
i=3       Migration     👎          0       2.0        0.00
i=4       Wonka         👍          1       2.32       0.43
i=5       The Marvels   👍          1       2.58       0.38

DCG = 1.00 + 0 + 0 + 0.43 + 0.38 = 1.81
```

**Interprétation :**
- Items pertinents en **positions hautes** contribuent plus
- Position 1 : contribution complète (÷ 1.0)
- Position 5 : contribution réduite (÷ 2.58)
- **Plus DCG est élevé, meilleur** est le ranking

---

### 6.2 Normalized DCG (NDCG@N)

**Problème avec DCG :**
- DCG varie selon nombre d'items pertinents
- Difficile de comparer entre utilisateurs

**Solution : Normaliser par DCG idéal**

**Formule :**
```
NDCG@N = DCG_u@N / DCG*_u@N
```

Où **DCG*_u@N** = meilleur DCG possible (items pertinents placés en top positions)

**Exemple (suite) :**

```
DCG actuel = 1.81

Classement IDÉAL (tous pertinents en haut) :
Position  Film          Pertinent  rel_ui  log₂(i+1)  Gain
────────────────────────────────────────────────────────────
i=1       Barbie        👍         1       1.0        1.00
i=2       Wonka         👍         1       1.58       0.63
i=3       The Marvels   👍         1       2.0        0.50
i=4       Anatomy       👎         0       2.32       0.00
i=5       Migration     👎         0       2.58       0.00

DCG* = 1.00 + 0.63 + 0.50 + 0 + 0 = 2.13

NDCG@5 = 1.81 / 2.13 ≈ 0.85 = 85%
```

**Interprétation :**
- **NDCG ∈ [0, 1]**
- NDCG = 1.0 → Ranking parfait ✅
- NDCG = 0.0 → Aucun item pertinent recommandé ❌
- NDCG = 0.85 → Ranking à 85% de l'optimal

**Avantages NDCG :**
- ✅ Normalisé : comparable entre utilisateurs
- ✅ Prend en compte l'ordre
- ✅ Standard dans la recherche d'information
- ✅ Variante : peut utiliser relevance graduelle (pas juste binaire)

## 7. 📋 Autres Métriques Utilisées {#other-metrics}

### 7.1 Mean Average Precision (MAP)

**Définition :**
Moyenne des précisions calculées à chaque position où un item pertinent apparaît.

**Formule :**
```
AP@N = (1/|relevant|) × Σ Precision@k × rel(k)
                        k=1 to N
```

**Caractéristiques :**
- Récompense avoir items pertinents tôt
- Populaire en information retrieval
- Sensible à l'ordre

---

### 7.2 Mean Reciprocal Rank (MRR)

**Définition :**
Inverse du rang du **premier** item pertinent.

**Formule :**
```
MRR = 1 / rank_of_first_relevant_item
```

**Exemple :**
```
Liste : [❌, ❌, ✅, ✅, ✅]
Premier pertinent à position 3
MRR = 1/3 ≈ 0.33
```

**Quand utiliser :**
- Quand seul le **premier** résultat compte
- Ex: recherche web, Question Answering

---

### 7.3 Area Under the ROC Curve (AUC)

**Définition :**
Aire sous la courbe ROC (Receiver Operating Characteristic).

**Principe :**
- Tracer True Positive Rate vs False Positive Rate
- Mesure capacité à discriminer pertinent vs non pertinent

**Interprétation :**
- AUC = 1.0 → Classification parfaite
- AUC = 0.5 → Aléatoire
- Utilisé pour évaluation binaire (pertinent/non pertinent)

---

### 7.4 Hit-Rank (HR@N)

**Définition :**
Proportion d'utilisateurs ayant **au moins 1** item pertinent dans Top-N.

**Formule :**
```
HR@N = #users_with_hit / #total_users
```

**Caractéristiques :**
- Métrique simple et interprétable
- Ne considère pas combien ou à quelle position

---

### 7.5 Average Reciprocal Hit-Rank (ARHR)

**Définition :**
Moyenne des inverses des rangs de **tous** items pertinents.

**Formule :**
```
ARHR = (1/|users|) × Σ (1/rank_of_hit)
```

**Caractéristiques :**
- Récompense hits en positions hautes
- Combine HR et position

## 8. 🎓 Résumé et Recommandations

### 8.1 Choisir la bonne métrique

| Objectif | Métrique recommandée |
|----------|---------------------|
| Précision ratings | MAE, RMSE |
| Top-N accuracy | Precision@N, Recall@N |
| Qualité ranking | NDCG@N, MAP |
| Premier résultat | MRR |
| Coverage générale | HR@N |
| Classification binaire | AUC |

### 8.2 Bonnes pratiques

1. **Utiliser plusieurs métriques**
   - Une seule métrique ne suffit pas
   - Accuracy + Diversity + Coverage

2. **Choisir split temporel si possible**
   - Plus réaliste pour production
   - Évite data leakage

3. **Offline → User Study → Online**
   - Pipeline d'évaluation progressive
   - Réduire risques avant déploiement

4. **Comparer à baseline**
   - Popularity baseline
   - Random baseline
   - Mesurer amélioration relative

5. **Significance testing**
   - Tests statistiques (t-test, bootstrap)
   - Assurer différences non aléatoires

---

## Conclusion

L'évaluation des systèmes de recommandation est **multidimensionnelle** :

✅ **Offline Evaluation** : Développement et comparaison rapide  
✅ **User Study** : Insights qualitatifs et UX  
✅ **Online Evaluation** : Validation finale avec impact réel  

**Aucune métrique n'est parfaite**, il faut :
- Combiner métriques accuracy, ranking, coverage, diversity
- Adapter méthode d'évaluation au contexte
- Toujours valider en production avec A/B tests

> "All models are wrong, but some are useful" - George Box
